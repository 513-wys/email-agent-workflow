## 1. 产品定义

Email Agent 是一个单用户、本机运行、中英双语、只读优先的邮件工作台。英文作为课程作业的默认交付语言，中文作为个人使用语言，两者共享同一套功能和数据。它连接 Gmail 或网易邮箱，将新邮件可靠同步到本地，完成安全检查、语义分类、行动事项提取、知识检索与跨邮件问答，并让用户能从每个结论回到证据片段和原始邮件。

三天目标不是完成完整生产版，而是交付一条可重复演示、可追溯的最小纵向闭环：

`可靠增量同步 → 多维分类 → 动态事项 → 本地知识索引 → 跨邮件 RAG 问答 → 来源引用 → 原邮件跳转`

### 1.1 本轮必须实现的用户价值

1. 重复点击同步不会重复入库、不会因读取而改变邮件未读状态，并能看到新增、跳过和失败数量。
2. 邮件不再只有一个粗粒度标签；用户能同时看到主分类、优先级、是否需要行动、截止时间和是否需要回复。
3. 行动事项从邮件中动态生成，并可追溯到产生它的邮件。
4. 已同步邮件可以被索引，用户可跨邮件提问；回答必须引用具体邮件证据。
5. 邮件列表、事项和问答引用都能跳到应用内详情，并在 Gmail 可定位时继续打开原邮件。

### 1.2 本轮明确不做

- 自动发信、自动回复、草稿审批和邮箱侧删除/归档。
- Outlook 原生 OAuth、多租户、团队权限、云端部署。
- 通用附件 OCR、复杂格式文档知识库、企业级向量数据库。
- 自动抓取任意邮件链接；现有官网抓取不作为三天主链路的依赖。
- 完整移动端重设计、完整安全加固和所有 `PROJECT_PLAN.md` 未完成项。

### 2.3 已确认缺口

| 缺口 | 当前行为 | 风险 |
|---|---|---|
| 增量同步 | 使用 IMAP sequence number、`UNSEEN SINCE` 和 `RFC822` | 标识不稳定、可能标已读、无法可靠断点续传 |
| 去重与更新 | `trace_id` 可基于 sequence number，写入用 `INSERT OR REPLACE` | 重复处理、行 ID 改变、引用失效 |
| 收件时间 | 保存邮件 `Date` 头 | 不能可靠定义新加坡“今日”窗口 |
| 分类结构 | 8 类 intent + priority；无置信度持久化 | 分类过粗，低置信度会静默落入资讯类 |
| 动态事项 | `requires_reply` 只存在于模型返回值，未入库；无事项表 | 无法形成可管理待办 |
| 知识库索引 | `kb_references` 永远为空 | 无检索语料和证据定位 |
| 跨邮件问答 | 无查询、检索、回答路由 | 不能综合历史邮件回答问题 |
| 来源引用 | 无片段级引用数据 | 回答不可核验 |
| 原邮件跳转 | 提取 `X-GM-MSGID`，但 URL 规则不完整；历史记录均无链接 | 用户无法回到真实来源 |
| 晨报范围 | 最近 100 条，不是严格今日 | 数量和事项会混入历史邮件 |

## 3. 分类模型

分类采用“一个主分类 + 多个正交维度”，避免把业务主题、紧急程度和下一步动作挤进同一个标签。

### 3.1 主分类 `category`

| 枚举 | 中文 | 典型内容 |
|---|---|---|
| `VERIFICATION_CODE` | 验证码 | OTP、2FA、邮箱验证 |
| `SECURITY_ALERT` | 安全提醒 | 登录异常、密码重置、账号风险 |
| `PAYMENT_BILLING` | 账单付款 | 发票、收据、扣款、退款、物流 |
| `MEETING_CALENDAR` | 会议日程 | 邀请、改期、取消、日程提醒 |
| `EDUCATION_NOTICE` | 教育通知 | 课程、注册、学校行政、校园服务 |
| `BUSINESS_INQUIRY` | 商务合作 | 报价、合作、供应商或销售线索 |
| `CUSTOMER_SUPPORT` | 客户支持 | 故障、投诉、产品问题 |
| `PROJECT_UPDATE` | 项目进展 | 团队同步、里程碑、交付状态 |
| `ACTION_REQUIRED` | 待办通知 | 明确要求用户完成某项操作但不属于以上类别 |
| `PERSONAL` | 个人邮件 | 一对一沟通、个人转发 |
| `NEWSLETTER` | 资讯订阅 | 行业简报、内容推荐 |
| `MARKETING` | 营销推广 | 促销、冷推销、群发广告 |
| `OTHER` | 其他/待确认 | 无法可靠归类或低置信度 |

### 3.2 正交维度

| 维度 | 字段与取值 | 决策原则 |
|---|---|---|
| 优先级 | `P0_CRITICAL` / `P1_HIGH` / `P2_NORMAL` / `P3_LOW` | 由影响范围、时效和用户关系共同决定 |
| 处理需求 | `requires_action: bool` | 邮件是否要求用户完成可执行动作 |
| 回复需求 | `requires_reply: bool` | 是否需要用户回复，而非仅点击或查看 |
| 时间状态 | `deadline_at`、`deadline_text`、`expiry_at` | 明确日期解析为时间；模糊表达保留原文，不臆造日期 |
| 置信度 | `confidence: 0..1` | 低于 0.65 时主分类为 `OTHER` 并标记待确认 |
| 语义标签 | `labels[]` | 项目、客户、课程、产品等可多选标签，不替代主分类 |
| 实体 | `entities[]` | 人、组织、金额、订单号、项目名等结构化线索 |
| 风险 | `risk_level`、`threat_score` | 继续由安全模块产生，分类模型不得降低安全结论 |

### 3.3 动态事项生成规则

一封邮件可产生零个或多个事项。事项至少包含标题、状态、优先级、来源邮件、证据片段和创建时间；有明确期限时才写入标准化截止时间。

- `requires_action=false` 时默认不生成事项。
- 验证码可生成短时效事项，但必须记录 `expiry_at`，过期后自动显示“已失效”。
- 同一来源邮件、同一规范化动作文本只生成一条事项。
- 新版本重跑分类时更新系统生成事项，不删除用户手动修改或已完成事项。
- 每个事项必须能跳回应用内邮件详情；有可信 provider 定位符时再显示“在原邮箱查看”。

### 4.1 确定性代码与模型边界

- 确定性代码负责 UID、时间、去重、状态迁移、事项幂等、链接生成、检索排名、引用 ID 和统计数字。
- 模型负责语义分类、摘要、动作表述和基于给定证据生成回答。
- 模型输出必须经过枚举与字段校验；失败进入明确降级状态，不得默认伪装成成功。
- RAG 回答只能引用检索返回的片段；没有足够证据时回答“现有邮件中没有足够依据”。

## 5. 数据结构基线

三天内采用向后兼容迁移：保留现有 `emails.id`，新增表通过外键引用它。不得清库或覆盖现有 24 封记录。

### 5.1 现有 `emails` 的兼容扩展

需要补充或可靠回填的字段：

| 字段 | 用途 |
|---|---|
| `account_id` | 区分邮箱账号；当前单账号也必须显式记录 |
| `provider` | `GMAIL` / `NETEASE_163` |

### 5.2 新增核心表

| 表 | 关键字段 | 约束 |
|---|---|---|
| `mail_sync_state` | `account_id`, `folder`, `uidvalidity`, `last_uid`, `last_synced_at` | `(account_id, folder)` 唯一；UIDVALIDITY 变化必须触发安全重建 |
| `processing_runs` | `id`, `started_at`, `finished_at`, `status`, `fetched`, `inserted`, `skipped`, `failed`, `error_summary` | 每次手动同步一条批次记录 |
| `email_analysis` | `email_id`, `category`, `priority`, `confidence`, `requires_action`, `requires_reply`, `deadline_at`, `deadline_text`, `labels_json`, `entities_json`, `model`, `prompt_version` | `email_id` 唯一；枚举受约束 |
| `action_items` | `id`, `email_id`, `fingerprint`, `title`, `details`, `status`, `priority`, `deadline_at`, `expiry_at`, `evidence_text`, `created_at`, `updated_at`, `user_modified` | `(email_id, fingerprint)` 唯一；状态为 `OPEN/DONE/DISMISSED/EXPIRED` |
| `knowledge_documents` | `id`, `source_type`, `source_id`, `title`, `source_url`, `content_hash`, `indexed_at` | 邮件作为首批知识文档；`(source_type, source_id)` 唯一 |
| `knowledge_chunks` | `id`, `document_id`, `chunk_index`, `text`, `embedding`, `token_count`, `metadata_json` | `(document_id, chunk_index)` 唯一；必须保留可展示原文片段 |
| `rag_queries` | `id`, `question`, `answer`, `model`, `created_at` | 保存问答历史但不保存密钥 |
| `rag_citations` | `query_id`, `chunk_id`, `email_id`, `rank`, `score`, `quoted_text` | 每条引用可回到 chunk、邮件详情和原邮件 |

### 5.3 引用对象

前端统一使用以下引用视图模型：

```json
{
  "citation_id": "cite_01",
  "email_id": 123,
  "subject": "邮件主题",
  "sender": "sender@example.com",
  "received_at": "2026-09-30T09:30:00+08:00",
  "snippet": "支持回答的原文片段",
  "detail_url": "/emails/123",
  "original_url": "https://mail.google.com/..."
}
```

`original_url` 可以为空，`detail_url` 不可为空。回答正文使用稳定引用编号 `[1]`、`[2]`，编号必须与引用卡片一一对应。

## 8. 三天实施顺序

### 第一天：先建立可靠的数据身份与来源链

目标：让“同一封邮件”在系统中有稳定身份，且始终能解释来自哪里。

1. 建立版本化迁移，备份后兼容扩展现有数据库；禁止清空 24 封历史记录。
2. 将 IMAP 摄取切换到 UID 与 `BODY.PEEK[]`，保存 `UIDVALIDITY`、`INTERNALDATE`、真实 Message-ID 和 provider ID。
3. 实现 account + folder + UID / Message-ID / content hash 的分层幂等键，并替换破坏性的 `INSERT OR REPLACE`。
4. 增加 `processing_runs` 与同步结果摘要。
5. 修正 Gmail 原文链接；无法精确回填的历史邮件提供受控 Gmail 搜索回退。
6. 完成增量同步的自动化测试和手工双击同步验证。

第一天退出条件：连续同步两次，第二次新增 0；邮件未读状态不变；新邮件显示真实收件时间；可从详情跳回 Gmail 或明确显示不可定位原因。

### 第二天：完成多维分类、动态事项与增量索引

目标：把可靠邮件记录转换为可执行信息和可检索知识。

1. 固化第 3 节分类 Schema，增加严格校验与低置信度 `OTHER` 路径。
2. 将分类、摘要、行动字段从 `emails` 展示字段中解耦到 `email_analysis`，兼容读取旧字段。
3. 建立 `action_items`，实现基于来源邮件和动作指纹的幂等生成、失效判断和来源跳转。
4. 增加事项列表；允许完成/恢复，但不触发任何外部邮箱动作。
5. 将邮件构造成 `knowledge_documents` 与 `knowledge_chunks`，只索引新增或内容变化的安全邮件。
6. 实现可替换的嵌入/检索接口；优先使用本地方案，模型不可用时给出明确状态。

第二天退出条件：演示邮件能落入正确主分类；至少一封邮件生成事项；重复分析不重复生成事项或切片；事项和切片均能回到来源邮件。

### 第三天：完成跨邮件问答、引用与端到端验收

目标：用真实引用把同步、理解和问答串成闭环。

1. 新增跨邮件问答页面/API：问题 → 检索 → 有界上下文 → 回答。
2. 在生成前固定引用编号，回答后校验编号，禁止模型创建不存在的来源。
3. 展示主题、发件人、收件时间、证据片段、详情链接和原邮件链接。
4. 修正晨报为今日查询，使用动态事项并附来源入口。
5. 增加无答案、模型失败、空索引和无原邮件链接等降级状态。
6. 运行第 9 节演示脚本与最小回归测试；记录未通过项，不用临时硬编码掩盖失败。

第三天退出条件：至少一个需要综合两封邮件的问题得到带引用回答；点击引用可到邮件详情并继续到 Gmail；证据不足的问题明确拒答；整个演示可重复执行。

## 9. 最终演示验收标准

演示使用一个受控 Gmail 测试账号或等价夹具，至少准备：会议变更、账单/付款、项目进展、验证码或安全提醒、资讯订阅各一封，其中至少两封围绕同一项目以支持跨邮件问题。

### 9.1 增量同步

- 首次同步展示批次结果：拉取数、新增数、跳过数、失败数。
- 第二次同步同一邮箱时新增数为 0，数据库邮件数不增长，已有邮件 ID 不变化。
- 同步前后的 Gmail 未读状态一致。
- 页面展示 Asia/Singapore 的真实收件时间，而不是处理时间或不可信的本机当前时间。

### 9.2 分类与事项

- 五类演示邮件进入符合第 3 节定义的主分类；低置信度样例进入“其他/待确认”。
- 每封邮件展示优先级、置信度、是否需行动、是否需回复和期限依据。
- 有明确行动要求的邮件生成事项；重复分析后事项数不增加。
- 事项可标记完成，完成状态在刷新后保持；每个事项可打开来源邮件详情。

### 9.3 索引、问答与引用

- 索引状态能显示文档数、片段数和最后更新时间。
- 问“项目 X 的最新进展和下一步是什么？”时，回答综合至少两封相关邮件。
- 回答中的每个关键结论都带 `[n]` 引用；引用卡显示原文片段，且片段确实支持该结论。
- 点击引用可进入应用内邮件详情；若存在 provider 定位符，可继续打开正确 Gmail 原邮件。
- 对“邮件中没有提到的预算是多少？”之类无依据问题，系统明确说明没有足够证据，不编造答案。

### 9.4 晨报与故障降级

- 晨报只统计新加坡时区当天邮件，数量与数据库查询一致。
- 晨报待办来自 `action_items`，每项有来源入口。
- 模型不可用时，同步与确定性统计仍可完成，分类/问答显示可操作的中文错误。
- 单封邮件解析或分析失败不终止整个批次，失败数量和阶段可见。

### 9.5 数据与范围保护

- 现有 24 封基线邮件未被清空；迁移后主键与详情链接保持有效。
- 不发送、不删除、不归档任何邮件，不自动点击邮件正文链接。
- 页面和日志不回显 DeepSeek Key 或邮箱授权码。
- 新功能未破坏现有仪表盘、邮件列表、详情、设置和手动晨报入口。

## 10. 开工与变更规则

1. 实现前先备份数据库并记录 Schema 版本；任何迁移都必须可重复执行。
2. 每个任务按“代码 + 自动化验证 + 页面可见 + 文档证据”四项闭环，不以文件存在视为完成。
3. 优先完成纵向闭环，禁止在三天内引入与验收无关的大型框架替换。
4. 任何模型结论都必须与确定性 ID、来源和时间关联；引用不得仅保存生成后的自然语言。
5. 遇到原邮件无法精确定位时必须诚实降级，不能生成猜测链接。
6. 每天结束时更新本文件第 6、7、8 节的状态与证据；长期任务状态仍回写 `PROJECT_PLAN.md`。
